이 문서는 Codex와 Hermes의 Writer가 Obsidian Vault에 기록할 때 따르는 정책의 단일 기준이다. Properties는 `PROPERTY_SCHEMA.md`, 본문 형식은 해당 템플릿을 따른다.

Writer는 검색·비교·기록을 담당한다. Organizer는 향후 Inbox 분류, 통합, 이동과 링크 정리를 담당할 별도 역할이며 아직 구현하지 않는다. 자동 기록 중에는 Organizer 작업을 수행하지 않는다.

## 1. 기본 원칙

1. Vault는 개인용 Second Brain이다.

2. 개발 지식, 프로젝트, 일정, 생각, 일상 등 다양한 정보를 관리한다.

3. 모든 내용을 기록하지 않고 장기적으로 유용한 정보를 우선한다.

4. 기존 노트의 내용을 보존하고 중복 생성을 방지한다.

5. 폴더는 정보의 용도, Properties는 속성, 내부 링크는 관계를 표현한다.

6. 노트는 사람이 읽기 쉽고 AI가 검색하기 쉬운 Markdown으로 작성한다.

7. 사실, 추론, 의견을 명확하게 구분한다.

8. 사용자가 기록하지 않은 개인 정보나 사실을 추측하지 않는다.


## 2. Vault Directory Rules

### 00-Inbox

Writer가 독립적인 새 지식과 분류·대상 노트가 불명확한 정보를 처음 기록하는 곳이다. 정리할 폴더를 추정할 수 있어도 독립적인 새 지식은 여기에서 시작한다.

- 빠르게 작성한 메모

- 정리되지 않은 아이디어

- 목적이 불명확한 내용


관련 노트가 있다는 이유만으로 기존 노트에 추가하지 않는다. 기존 지식의 단순 보완인지 독립적인 새 지식인지 아래 기록 처리 정책으로 판단한다.

### 01-Journal

시간 중심의 기록을 저장한다.

- 일기

- 일일 활동

- 주간 및 월간 회고

- 개인적인 경험


파일명 예시: `2026-10-30.md`

같은 날짜의 Daily 노트가 있다면 중복 생성하지 않는다.

### 02-Projects

명확한 목표와 완료 조건이 있는 활동을 저장한다.

- 소프트웨어 개발

- 개인 프로젝트

- 프로젝트 아키텍처

- 설계 결정

- 문제 해결 기록


프로젝트 단위의 하위 폴더를 생성할 수 있다.

예시:

```
02-Projects/
└── Flux/
    ├── Flux.md
    ├── Architecture.md
    ├── Decisions/
    └── Troubleshooting/
```

이 구조는 정리된 프로젝트 문서의 용도를 설명한다. Writer의 신규 기록 위치와 기존 프로젝트 노트 갱신은 아래 기록 처리 정책을 따른다. 재사용 가능한 독립 지식은 Inbox에서 시작하고 실제 존재하는 프로젝트 노트와 연결한다.

### 03-Areas

지속적으로 관리해야 하는 삶의 영역을 저장한다.

- 커리어

- 건강

- 재무

- 생활 관리

- 인간관계


완료 시점이 명확하지 않은 지속적 책임과 관리 기준을 다룬다.

구체적인 달성 목표가 있는 활동은 프로젝트로 분류할 수 있다.

### 04-Knowledge

재사용 가능한 지식을 저장한다.

- 프로그래밍 언어

- 운영체제

- 네트워크

- 데이터베이스

- 경제 및 금융 지식

- 일반 상식과 학습 내용


하나의 노트는 가능한 한 하나의 핵심 개념을 설명한다.

특정 프로젝트에 종속되지 않는 설명을 우선한다.

### 05-Resources

외부 자료에 대한 정보를 저장한다.

- 책

- 논문

- 기술 문서

- 웹사이트

- 강의

- 참고 링크


원본 출처를 명확하게 기록한다.

원본 자료의 요약과 개인적인 해석을 구분한다.

### 06-Archive

사용하지 않거나 종료한 자료를 보관한다.

- 완료된 프로젝트

- 오래된 기록

- 비활성 노트


아카이브 이동 시 기존 파일명과 링크의 유효성을 확인한다.

사용자의 승인 없이 기존 노트를 아카이브하거나 삭제하지 않는다.

### 99-System

Vault 운영에 필요한 설정을 저장한다.

- `Templates/`: 노트 템플릿

- `AI/`: AI 작성 및 관리 규칙

- `Attachments/`: 이미지, 첨부파일

- `Dashboards/`: 대시보드


일반 지식 노트를 이 폴더에 저장하지 않는다.

## 3. Writer 기록 처리 정책

기록 후보마다 다음 순서로 판단한다. 같은 대화에서 앞서 검색했어도 새로운 후보는 관련 검색을 수행한다.

1. 기록 가치와 민감 정보 허용 범위를 확인한다.
2. `search_notes`로 동일하거나 유사한 기존 지식을 검색한다. 결과가 불충분하면 핵심 단어를 바꾸어 확인한다.
3. 관련 노트를 `read_note`로 읽어 실제 내용·맥락·출처·이력과 새 정보의 차이를 비교한다.
4. 아래 표에 따라 저장 대상과 create/append를 정한다. 주제나 폴더가 같다는 사실만으로 보완이라고 판단하지 않는다.
5. 기존 스키마의 `type`과 해당 템플릿을 적용하고 한국어로 새 정보만 기록한다. 한 노트에는 가능한 한 하나의 핵심 지식을 담는다.
6. 실제 존재하는 관련 노트만 연결하고 저장 결과의 실제 경로와 내용을 확인한다.

| 기록 후보 | 처리 |
| --- | --- |
| 독립적인 새 지식 | `00-Inbox/`에 새 노트 생성 |
| 분류 또는 대상 노트가 불명확한 정보 | `00-Inbox/`에 새 노트 생성 |
| 명확한 기존 지식의 단순 보완 | 최신 SHA256으로 해당 노트에 append |
| 작업 진행 기록 | `01-Journal/`의 해당 날짜 노트에 생성 또는 append |
| 확정된 프로젝트 결정 | 명확히 확인한 해당 프로젝트 노트에 날짜·근거와 함께 append |
| 이미 충분히 기록된 내용 | 저장하지 않고 `skip_turn(reason: duplicate)` |

- 기존 노트의 핵심 개념·목적을 유지하면서 빠진 설명이나 검증 결과를 보충하는 경우에만 단순 보완으로 판단한다.
- 별도 제목과 맥락으로 재사용할 수 있는 독립 지식은 같은 주제의 노트가 있어도 Inbox에 생성한다. 분류가 애매하면 Inbox를 선택한다.
- 확정된 프로젝트 결정도 해당 프로젝트 노트를 특정할 수 없으면 Inbox에 기록한다. 프로젝트 관계를 추측하거나 새 프로젝트 구조를 자동으로 만들지 않는다.
- 여러 종류의 정보가 섞이면 기록 후보를 나누고 각 후보에 이 정책을 적용한다.
- Journal은 기록할 작업이 이루어진 날짜를 사용한다. 날짜가 명시되지 않은 현재 작업은 현재 서울 날짜를 사용하며, 같은 날짜의 Daily 노트를 재사용한다. 과거 날짜는 추측하지 않는다.
- 파일명 충돌은 보완의 근거가 아니다. 기존 파일을 읽고 다시 검색한 뒤, 서로 다른 내용이면 구별되는 파일명으로 생성한다. 기존 파일을 덮어쓰지 않는다.
- 서버가 동일 본문을 발견하면 노트를 바꾸지 않고 기존 경로를 반환할 수 있다. 요청 경로에 새 파일이 생겼다고 가정하지 않는다. 표현이 다른 의미상 중복은 Writer가 검색·비교로 판단한다.
- 규칙·템플릿은 읽기 대상으로 사용한다. Writer는 신규 노트를 정리된 폴더로 옮기거나 기존 노트를 분류·통합·삭제·일괄 수정하지 않는다.

## 4. Automatic Knowledge Extraction

AI 에이전트는 작업 과정에서 다음 정보를 기록 후보로 판단한다.

### 기록할 정보

- 새롭게 학습한 개념

- 중요한 설계 결정과 근거

- 문제의 원인과 검증된 해결 방법

- 반복적으로 활용할 수 있는 명령어나 설정

- 프로젝트의 주요 아키텍처 변경

- 사용자가 명시한 목표 및 중요한 생각

- 재사용 가치가 높은 실험 결과


### 기록하지 않을 정보

- 단순 인사나 일반 대화

- 일회성 오류 메시지만 있는 기록

- 맥락 없는 코드 조각

- 이미 충분히 기록된 중복 정보

- 검증되지 않은 추측을 확정된 사실로 표현한 내용

- 사용자가 저장을 원하지 않는 정보

- API 키, 비밀번호, 인증 토큰 등 민감한 비밀 정보


개인 일기, 건강, 재무, 인간관계처럼 민감할 수 있는 내용은 사용자가 명시적으로 기록을 허용한 범위에서만 자동 저장한다.

## 5. Note Update Rules

Writer의 기존 노트 갱신은 append로 새 정보만 추가한다.

1. 대상 노트를 먼저 읽고 `read_note`가 반환한 최신 SHA256을 사용한다. 변경 충돌이 있으면 다시 읽고 비교한다.
2. 기존 본문·사용자 작성 내용·생성일·상태·출처·내부 링크·기록 이력을 보존한다. 전체 내용을 무조건 덮어쓰거나 템플릿 전체를 다시 추가하지 않는다.
3. 이미 기록된 설명을 반복하지 않고 보완할 차이만 추가한다.
4. 같은 주제의 새로운 결정이나 중요한 상태 변경은 날짜, 변경 내용, 근거 및 이전 결정과의 관계를 구분해 추가한다. 이전 결정을 삭제하거나 현재도 유효한 사실처럼 조용히 바꾸지 않는다.
5. 확인되지 않은 충돌은 사실과 미확인 내용을 구분해 기록하고 임의로 결론내리지 않는다.
6. 실제 내용이 변경될 때만 `updated`를 갱신한다. 동일 내용 재시도는 기존 파일과 수정일을 보존한다.

기존 기록을 재구성하거나 통합하는 작업은 Writer의 자동 기록 범위가 아니다. 별도로 승인된 정리 작업 없이 삭제·이동·이름 변경·대규모 재작성을 수행하지 않는다.

## 6. Note Linking Rules

- 관련된 노트는 `[[WikiLink]]`로 연결한다.

- 프로젝트 문서와 독립적인 지식 문서를 연결한다.

- 의미 없는 과도한 링크는 생성하지 않는다.

- 존재하지 않는 노트는 자동으로 생성하지 않는다.

- 새로운 개념 노트가 필요하면 생성 규칙을 다시 적용한다.


예시:

`[[Flux]]` → `[[kqueue]]` → `[[Event Loop]]`

## 7. Template Rules

새 노트를 생성할 때 `99-System/Templates/`의 해당 템플릿을 우선 적용한다.

템플릿이 존재하지 않으면 공통 Properties와 일관된 Markdown 구조를 사용한다.

템플릿에 포함된 `{{date}}`, `{{title}}` 등의 변수는 실제 값으로 치환한다.

Obsidian 템플릿 변수나 임시 안내 문구를 최종 생성 노트에 남기지 않는다.

## 8. Writing Style

- 기본 작성 언어는 한국어로 한다.

- 기술 용어 및 API 이름은 원문을 유지한다.

- 제목은 명확하고 구체적으로 작성한다.

- 불필요한 반복과 장황한 설명을 피한다.

- 코드에는 언어가 지정된 코드 블록을 사용한다.

- 확실하지 않은 내용은 불확실성을 표시한다.

- 참고 자료가 있다면 출처를 기록한다.


## 9. Safety Rules

- 사용자의 명시적인 요청 없이 노트를 삭제하지 않는다.

- 기존의 개인 기록을 무단으로 재작성하지 않는다.

- 노트 이동이나 이름 변경 시 링크의 유효성을 확인한다.

- 대규모 파일 변경 전에는 Git 등으로 복구 가능한 상태를 확보한다.

- 실행 결과, 테스트 결과, 출처를 조작하거나 만들어내지 않는다.

- 시스템 폴더 및 설정 파일을 임의로 변경하지 않는다.

- Vault 외부 파일을 읽거나 수정하는 작업은 허용된 범위에서만 수행한다.


## 10. Rule Priority

규칙이 충돌할 경우 다음 순서로 적용한다.

1. 사용자의 명시적인 지시

2. 보안 및 데이터 보존 원칙

3. `PROPERTY_SCHEMA.md`

4. `NOTE_RULES.md`

5. 개별 노트 템플릿


AI 에이전트는 규칙이 모호하거나 기존 데이터를 손상시킬 가능성이 있으면 자동 수정을 중단하고 사용자에게 확인한다.
